# RuleSend 제품 기획서

문서 상태: 제품 목표와 Alpha 범위. 아래의 목표·수용 기준은 구현 완료를 뜻하지 않는다. 구현의 API·데이터·명령 계약은 [IMPLEMENTATION_CONTRACT.md](IMPLEMENTATION_CONTRACT.md) 및 [CLI.md](CLI.md)를 따르며, 실제 제공 기능과 검증 결과는 README 및 릴리스 기록에서 확인한다.

제품명: **RuleSend**. 공개 저장소: https://github.com/pilgrim13/rulesend. 운영 방식: 개인이 직접 운영하는 중앙 Hub와 각 기기의 Agent. 공개 저장소에는 제품 코드·가상 예제·운영 설명만 포함한다.

## 1. 해결할 문제

같은 사람이 여러 기기와 AI 도구를 쓰면 공통 규칙의 원본, 실제 설치 파일, 대화에서 읽은 규칙이 서로 달라질 수 있다. Git에 새 버전을 올렸거나 파일을 복사했다는 사실만으로 모든 기기와 앱에 규칙이 적용됐다고 말할 수 없다.

RuleSend는 **승인한 AI 규칙을 선택한 기기·앱에 전달하고, 어디까지 확인됐는지를 보여주는 서비스**다. 핵심 화면은 파일 탐색기가 아니라 규칙 버전과 배포 대상의 상태표다. Markdown 열람·편집, 이력·충돌·복구는 이 흐름 안에 둔다.

### 사용자에게 줄 답

- 지금 승인된 공통 규칙은 무엇인가?
- 어떤 기기와 앱이 어떤 버전을 실제 파일에 설치했는가?
- 무엇이 오프라인·충돌·권한 오류로 멈췄는가?
- 파일 설치 이후 앱이 읽었는지, 실제 행동까지 확인했는지 근거가 있는가?
- 바꾸고 되돌리는 작업을 한곳에서 안전하게 할 수 있는가?

## 2. 제품 원칙

1. **승인 원본과 관측 상태를 분리한다.** Hub의 목표 버전과 Agent의 마지막 확인 결과를 각각 보관한다.
2. **게시가 배포를 시작한다.** 편집 중인 초안은 Agent에 자동 설치하지 않는다.
3. **기기에서 허용한 대상에만 쓴다.** 웹 화면이 새로운 로컬 경로나 원격 명령 권한을 만들 수 없다.
4. **기존 파일을 존중한다.** 규칙의 관리 블록 밖 내용은 그대로 보존한다. 원치 않는 전역 폴더 동기화는 하지 않는다.
5. **모르는 상태는 모른다고 표시한다.** 파일 저장, 앱 로드, 행동 검증을 하나의 성공 표시로 합치지 않는다.
6. **충돌에서는 내용을 보존한다.** 마지막 저장 시각만 보고 한쪽 내용을 버리지 않는다.
7. **원본 하나, 적용 대상 여러 개.** 같은 규칙 팩에서 앱별 적용 파일을 만들되 앱의 규칙 발견 방식을 과장하지 않는다.

## 3. 대상 사용자와 첫 제품 범위

### 첫 사용자

- 개인 규칙을 여러 macOS·Linux 기기에 유지하는 한 사람.
- Codex와 Claude Code처럼 로컬 Markdown 지침을 읽는 도구를 함께 쓰는 사람.
- 직접 Hub를 운영하고 백업·복구 책임을 맡을 수 있는 사용자.

### Alpha 범위

- 한 명의 관리자, 한 개의 권위 있는 Hub, 복수 Agent.
- 규칙 팩 생성, UTF-8 Markdown/텍스트 편집, 미리보기, 명시적 게시. 상세 변경 비교 화면은 후속 개선이 가능하다.
- 승인 버전별 변경 이력과 이전 내용으로 새 버전을 게시하는 되돌리기.
- 로컬에서 등록한 대상 파일과 관리 블록에 대한 적용.
- 간편한 기기 등록, 마지막 연결 시각, 기기 인증 폐기.
- 중앙에서 수동/주기 모드와 간격 변경, 지금 동기화 요청.
- 버전·해시·확인 시각을 근거로 한 기기별 설치 현황.
- 오프라인, 로컬 수정, CAS 충돌, 적용 실패의 보존과 표시.
- 팩당 UTF-8 Markdown 최대 128 KiB. 적용 후 전체 파일은 Codex 대상 최대 32 KiB, Claude Code/custom 대상 최대 128 KiB. 관리 블록 밖 기존 내용도 전체 파일 제한에 포함한다.
- 기본 로컬 접속, 원격 접속 시 HTTPS 또는 올바르게 구성된 HTTPS 역방향 프록시.

### Alpha에서 약속하지 않는 것

- Windows Agent 실행 지원(후속 단계).
- 로컬 수정본의 Hub 자동 업로드, 원격 로컬 차이 열람, 자동 병합.
- 규칙 팩/대상 파일 삭제 전파, tombstone, 범용 작업 ID 프로토콜.
- 앱 로드·행동 검증 근거의 자동 수집 또는 기록 UI. Alpha는 항상 미확인으로 표시한다.

- 모든 종류의 파일과 폴더를 동기화하는 범용 Syncthing 대체품.
- 여러 Hub의 자동 합의, Hub 없이 동작하는 기기 간 P2P 전파.
- 동시 편집기의 실시간 공동 편집 또는 임의의 Markdown 자동 병합.
- 일반 Claude 채팅·Cowork·Codex의 모든 실행 방식에 대한 자동 로드 증명.
- 기존 대화 전체의 규칙을 자동 갱신했다는 보장.
- 회사 규칙과 개인 규칙의 자동 우선순위 판단 또는 회사 정책 준수 인증.
- 원격 셸, 임의 명령 실행, 원격 경로 생성 권한, Agent의 권한 상승.
- 심볼릭 링크, 특수 파일, 소유권·ACL·확장 속성의 동기화.
- 기업 다중 사용자·SSO·조직별 권한 체계, 무중단 고가용성.
- 외부 편집기와 같은 파일을 동시에 쓰는 모든 상황에서의 무손실 보장.

Alpha Agent의 목표 실행 환경은 macOS와 Linux다. Windows는 후속이다. 지원 운영체제의 빌드 성공과 실제 파일 시스템 동작 검증은 별개다. 릴리스에는 운영체제별 검증 범위를 적는다.

## 4. 개념과 데이터

| 개념 | 의미 |
| --- | --- |
| 규칙 팩 | 이름·설명·내용·승인 버전·배포 범위를 가진 규칙 묶음 |
| 초안 | Hub에서 편집 중이며 아직 게시되지 않은 내용 |
| 게시 버전 | 관리자가 내용을 확인하고 게시한 변경 불가 버전 |
| 기기 | 개별 인증과 연결 상태를 가진 Agent 설치 단위 |
| 대상 매핑 | 기기에서 허용한 규칙 팩 → 앱/용도 → 로컬 파일/관리 블록 관계 |
| 관리 블록 | RuleSend가 수정하도록 사용자가 지정한 파일 안의 구간 |
| 기준 버전 | 초안 편집을 시작할 때 관측한 Hub 버전 |
| 설치 확인 | Agent가 대상 파일에 반영한 뒤 다시 읽어 확인한 버전·해시·시각 |
| 앱 로드 | 별도 근거가 필요한 개념. Alpha에서는 항상 미확인 |
| 행동 검증 | 별도 근거가 필요한 개념. Alpha에서는 항상 미확인 |

Hub는 서버가 부여한 버전으로 변경 순서를 판단한다. 기기의 파일 수정 시각이나 벽시계는 동시 변경의 승자를 정하는 기준이 아니다. 설치 확인에는 게시 버전뿐 아니라 실제 설치한 관리 블록의 해시를 함께 기록한다. 변환이 있는 적용 방식은 원본 해시와 설치 결과 해시를 구분한다.

## 5. 첫 사용 흐름

1. 사용자가 자기 서버 또는 컴퓨터에서 Hub를 시작한다.
2. 관리 인증을 설정하고 로컬 화면에 접속한다. 외부 공개 전 HTTPS 및 백업 설정을 확인한다.
3. 공통 규칙 Markdown을 붙여 넣거나 가져와 규칙 팩 초안을 만든다. 회사 자료를 개인 서버에 자동으로 가져오지 않는다.
4. 변경 내용을 확인하고 첫 버전을 게시한다. 게시 범위가 화면에 보인다.
5. Hub에서 짧은 유효기간의 일회용 기기 등록 토큰을 만든다.
6. 각 기기에서 Agent를 설치·등록한다. 토큰은 URL이나 저장소에 넣지 않는다.
7. 기기에서 로컬 대상 파일과 적용 방식을 선택한다. Alpha는 대상·팩·어댑터를 출력하고 파일 적용은 별도 실행한다. 전체 내용의 적용 전후 미리보기는 후속이며, 사용자는 게시본과 기존 파일을 확인한다.
8. Agent가 등록한 매핑에만 게시 버전을 적용하고 실제 파일을 다시 읽어 확인한다.
9. Hub는 기기별 설치 확인을 표시한다. 앱 로드와 행동 검증은 근거가 없으면 각각 미확인이다.

기기 등록은 설치 허용과 다르다. 등록만으로 홈 폴더나 앱 전역 설정에 접근하도록 만들지 않는다.

## 6. 규칙 수정과 게시

### 웹에서 수정

1. 기존 게시 버전을 기준으로 초안을 연다.
2. 편집·미리보기·차이를 확인한다. 저장은 초안 저장이다.
3. 게시 전 현재 내용과 대상 팩을 확인한다. 대상 기기와 이전/새 버전은 현황과 이력에서 확인할 수 있어야 한다. 상세 비교·확인 화면은 UX 개선 항목이다.
4. 사용자가 게시를 실행하면 Hub가 기준 버전을 검사한다.
5. 다른 게시가 먼저 있었다면 자동 덮어쓰지 않고 충돌을 표시한다.
6. 게시 성공 뒤 Agent 정책에 따라 전파한다. 게시 완료를 설치 완료로 표시하지 않는다.

### 기기에서 수정

- 관리 블록 밖 변경은 사용자 소유다. 이후 적용에도 바이트 그대로 보존한다.
- 관리 블록 안의 로컬 수정은 게시 버전에서 벗어난 상태로 감지한다.
- 로컬 수정 내용은 해당 기기의 파일과 복구본으로 보존하고 Hub에는 충돌 상태만 알린다. Alpha는 로컬 수정 본문을 업로드하지 않는다.
- 사용자는 기기에서 로컬 차이를 확인하고 필요한 내용을 Hub 초안에 수동 반영한다. 충돌을 해결하기 전 자동 재시도로 덮어쓰지 않는다.
- 원격 버전과 로컬 편집이 동시에 생기면 둘을 보존하고 해당 매핑 적용을 멈춘다.
- 파일 자체가 사라진 경우 경로 오류, 외부 삭제, 정책상 삭제를 구분한다. 파일이 없다는 관측만으로 팩 전체를 삭제하지 않는다.

### 되돌리기

이전 버전의 내용을 새 버전으로 게시한다. 버전 번호를 과거로 되감거나 이력을 삭제하지 않는다. 기기별 이전 파일 복구는 그 이후 사용자 변경과 충돌할 수 있으므로 복구 전 차이를 확인한다.

## 7. 앱 적용과 기존 규칙 보존

첫 적용 대상은 **로컬 Markdown 규칙 파일**이다. Codex용 `AGENTS.md`와 Claude Code용 `CLAUDE.md` 프로필은 파일 용도를 안내하는 어댑터다. 실제 탐색 경로·범위·중첩 규칙은 설치된 앱과 실행 방식에 맞춰 확인해야 한다.

- 대상 경로는 기기에서 직접 등록한다. 서버가 임의 절대 경로를 내려보내 실행시키지 않는다.
- 관리 블록은 팩 식별자가 포함된 시작/끝 표식으로 구분한다.
- Alpha는 대상 파일당 관리 블록 하나를 기본으로 해 중첩·우선순위 충돌을 줄인다.
- 최초 도입 시 블록이 없는 파일에는 명시적 로컬 등록을 거쳐 이후 적용 때 블록을 추가한다. Alpha 등록은 대상 요약을 출력하며 전체 내용 미리보기는 제공하지 않는다.
- 기존 다른 도구의 관리 표식은 자동 인수하지 않는다. 인수·이관은 별도 비교와 승인을 거친다.
- 중복 표식, 잘못 닫힌 표식, 잘못된 인코딩은 적용 오류다. 추측해서 파일을 고치지 않는다.
- 수정할 구간 이외의 내용, 줄바꿈, 사용자 주석을 가능한 한 원래 바이트로 보존한다. 관리 블록 경계의 줄바꿈 규칙은 명시적으로 정의하고 시험한다.
- 관리 블록 본문에 동일한 구분 표식을 넣지 못하게 검증한다.
- 동일 경로의 중복 매핑과 허용 루트가 겹쳐 의도치 않게 이중 관리되는 구성을 거절한다.

앱별 자료의 분리·참조 파일 지원·템플릿 변환은 명시적인 어댑터 확장이다. 일반 채팅의 프로젝트 지침 업로드나 서비스 API 연결은 독립 기능으로 취급한다.

## 8. 화면 구성

### 전체 현황

- 상단: 현재 게시된 규칙 팩과 마지막 게시 시각, 대응이 필요한 기기 수.
- 기본 표: 기기 / 앱·대상 / 목표 버전 / 설치 버전 / 앱 로드 / 행동 확인 / 마지막 확인 / 오류.
- 필터: 팩, 기기, 앱, 상태. 오류와 오래된 관측을 먼저 찾을 수 있다.
- 기기 연결 상태는 별도 표시한다. 연결됐다고 규칙이 최신이라는 의미는 아니다.

### 규칙 편집

- 왼쪽: 규칙 팩과 버전 목록.
- 가운데: 편집기와 Markdown 미리보기, 초안/게시본 구분.
- 오른쪽: 배포 대상 및 최근 적용 결과.
- 작업: 초안 저장, 게시본과 비교, 게시, 이전 내용으로 새 초안 만들기.
- Alpha는 충돌 상태와 로컬 확인 방법을 안내한다. 원격에서 로컬 본문을 함께 보는 병합 화면은 후속이다.

### 기기 상세

- 기기 이름, 식별자 일부, 마지막 연결, Agent 버전, 인증 상태.
- 로컬에서 등록한 매핑의 표시 이름과 앱 유형. 민감한 전체 경로를 공개 로그나 기본 목록에 노출하지 않는다.
- 목표/관측 버전, 적용 오류, 현재 정책, 마지막 요청과 완료 시각.
- 작업: 지금 동기화 요청, 일정 변경, 인증 폐기.
- 새 로컬 경로의 등록·변경은 해당 기기에서만 수행한다는 안내.

### 시각·접근성 원칙

- 차분한 배경, 명확한 타이포그래피, 충분한 여백과 선택적 강조색.
- 상태는 색뿐 아니라 아이콘과 텍스트로 표현한다.
- 작은 화면에서도 핵심 상태·차이·작업을 확인할 수 있게 한다.
- 키보드 탐색, 명확한 입력 라벨, 포커스 표시, 오류의 다음 행동을 제공한다.
- 외부 CDN·폰트·분석 도구 없이 UI가 동작하도록 한다.
- Markdown의 임의 HTML·스크립트는 실행하지 않는다.

## 9. 상태와 성공의 정의

| 상태 | 의미 | 필요한 다음 행동 |
| --- | --- | --- |
| 미등록 | Agent 또는 대상 매핑이 아직 없음 | 기기에서 등록 |
| 대기 | 게시 버전이 있지만 아직 확인 응답 없음 | 일정 또는 다음 연결 대기 |
| 확인 중 | Agent가 대상과 기준 버전을 비교 중 | 결과 대기 |
| 적용 중 | 파일 반영 중이며 검증 응답 전 | 결과 대기 |
| 설치 확인 | Agent가 게시 버전과 설치 내용을 실제 파일에서 확인 | 필요하면 앱 로드 검증 |
| 변경 감지/충돌 | 설치 이후 로컬 관리 블록이 달라짐 | 기기에서 차이 검토 |
| 충돌 | 기준 버전이 달라 자동 적용 불가 | 두 내용 검토 |
| 실패 | 권한·용량·경로·내용 검증 등 오류 | 구체적 원인 해결 후 재시도 |
| 오프라인/확인 오래됨 | 마지막 관측 이후 현재 파일 상태를 알 수 없음 | 재연결·재확인 |
| 인증 폐기 | Hub 접근 권한이 폐기됨 | 필요하면 새로 등록 |

별도의 두 열은 다음처럼 관리한다.

- **앱 로드:** Alpha에서는 항상 미확인. 이후 확인 기능에는 앱·세션·규칙 버전·방법·시각의 근거가 필요하다. 단순 프로세스 실행이나 파일 존재로 확인을 대신하지 않는다.
- **행동 검증:** Alpha에서는 항상 미확인. 이후 확인 기능에는 시나리오·기대 행동·결과·시각이 필요하며, 미래의 모든 모델 행동을 보장하는 인증이 아니다.

관측에는 유효 시간 개념을 둔다. 기기가 오프라인이 되면 과거의 설치 확인 기록은 보존하되 현재도 설치되어 있다고 단정하지 않는다. 화면에는 “v3 설치 확인 · 마지막 확인 2일 전 · 현재 오프라인”처럼 표시한다. 새 게시 뒤 이전 버전 응답은 최신 설치 확인으로 취급하지 않는다.

## 10. 기술 구조

```text
관리자 브라우저 ── HTTPS ── Hub
                            │
                    규칙·버전·정책·감사 기록
                            │
               HTTPS 요청/응답 및 변경 확인
                     ┌──────┴──────┐
                 Agent A        Agent B
                     │              │
              허용한 규칙 파일  허용한 규칙 파일
```

- Go 단일 실행 파일의 `hub`/`agent` 하위 명령을 기본으로 한다.
- UI는 실행 파일에 포함하는 HTML/CSS/JavaScript로 시작한다. 별도 프런트엔드 빌드 서버는 필요하지 않다.
- Hub는 SQLite에 게시 버전, 초안, 기기, 정책, 관측, 감사 이벤트를 저장한다.
- Agent는 로컬 설정·기준 버전·미완료 작업·백업 정보를 지속 저장한다. 프로세스 재시작으로 미전송 변경을 잃지 않아야 한다.
- 모든 Agent가 Hub로 나가는 연결을 사용한다. Agent의 원격 수신 포트와 원격 셸을 열지 않는다.
- 콘텐츠는 규칙 팩의 게시된 Markdown 전체를 전송한다. 범용 파일 전송, 블록 단위 최적화와 P2P는 범위에서 제외한다.
- 파일·SQLite 변경을 하나의 원자적 트랜잭션처럼 가정하지 않는다. 중단 후 재검사로 복구하는 상태 전이를 둔다.
- 구현 단위는 규칙 팩 초안의 CAS와 변경 불가 게시 버전이다. 범용 폴더 동기화 엔진을 전제로 하지 않는다.

### 변경 처리 불변 조건

1. 초안 저장과 게시에는 기준 초안 버전을 검사한다. 오래된 기준은 충돌로 거절하고 제출 내용을 사용자가 보존할 수 있게 한다.
2. 게시된 버전은 변경하지 않는다. 이전 내용으로 돌아갈 때도 새 초안과 새 게시 버전을 만든다.
3. Agent는 쓰기 전 로컬 기준과 현재 파일을 비교한다. 원격 버전이 최신이어도 로컬 미반영 변경을 덮어쓰지 않는다.
4. 파일은 같은 파일 시스템의 임시 파일에 쓴 뒤 검증·교체한다. 이전 전체 파일은 보호된 백업에 보존한다.
5. 저장 후 다시 읽은 내용과 관리 블록 해시가 기대값과 같을 때만 설치 확인을 보낸다. 해시가 다르면 실패 또는 충돌이다.
6. 루트/대상 접근 실패, 권한 오류를 삭제 요청으로 해석하지 않는다. Alpha에는 원격 삭제 기능이 없다.
7. 프로세스 중단 뒤에는 영속적인 적용 기록과 실제 파일을 비교한다. 모호한 결과는 충돌이며 자동 성공 처리하지 않는다.
8. 같은 파일에는 팩 하나만 적용한다. 로컬 등록과 안전 경로 검사가 Hub 정책보다 우선한다.
9. 외부 변경 확인은 폴링/주기 재검사로 시작한다. 파일 감시 최적화는 후속이다.

외부 프로그램의 파일 쓰기를 RuleSend가 잠글 수는 없다. 검사와 교체 사이에 또 쓰기가 발생할 수 있으므로, 재검사·이전 내용 백업·복구 가능한 교체를 하더라도 모든 경쟁 상황에서 무손실을 보증하지 않는다. 중요한 규칙은 게시 이력과 독립 백업을 유지하고, 같은 대상에 여러 자동 쓰기 도구를 겹쳐 운영하지 않는 것이 권장된다.

## 11. 동기화 정책

- **주기 모드:** 중앙 정책의 15~86,400초 간격에 따라 게시 버전과 로컬 상태를 확인한다. Agent의 연결·정책 확인은 약 15초마다 수행한다.
- **수동 모드:** 명시적 요청 때 콘텐츠 적용을 진행한다. 최초 등록만으로 적용하지 않는다. 연결 상태·정책 조회는 계속할 수 있다.
- **일시 중지:** 주기·수동 요청·명시적 한 번 실행 모두 적용을 멈춘다. 지금 동기화 요청은 일시 중지를 해제하지 않는다.
- **지금 동기화:** Hub의 요청 세대를 올린다. Agent는 마지막 처리 세대와 비교해 새로운 요청만 수행한다. 명시적 로컬 한 번 실행도 일시 중지되지 않은 현재 게시본을 적용한다.
- UI는 요청 접수와 실행 완료를 구분한다. 오프라인 기기에는 다음 연결 때 처리할 대기로 남는다.
- 짧은 간격은 최소값을 두고, 실패 재시도에는 제한된 지연 증가와 분산을 적용한다.
- 중앙 정책은 기존 로컬 허용 범위 안의 일정·대상 활성화만 다룬다. 새 경로 허용과 임의 명령은 정책에 포함하지 않는다.
- 수동 요청 처리 중 새 세대가 오면 요청을 유실하지 않아야 한다.
- 재시작·절전 복귀 뒤 놓친 예약을 무한 반복하지 않고 현재 게시 상태를 재확인한다.

## 12. 보안과 운영

### 인증과 전송

- Hub는 기본적으로 loopback에만 바인딩한다. 평문 원격 운영은 거절한다.
- 역방향 프록시는 내부 loopback 연결, 외부 HTTPS, 신뢰할 프록시 범위가 명확한 구성을 사용한다.
- 관리 인증과 기기 인증을 분리한다. 기기 인증으로 규칙을 게시하거나 다른 기기를 관리할 수 없다.
- 등록 토큰은 짧은 만료·일회 사용·기기/팩 범위를 갖고, 서버에는 검증용 해시만 저장한다.
- 등록 후의 기기 인증도 폐기 가능해야 한다. 비밀은 응답에서 필요한 순간에만 전달하고 로그에 남기지 않는다.
- TLS 검증을 건너뛰는 운영 옵션을 기본 사용법으로 제시하지 않는다.
- 브라우저의 인증정보를 URL에 넣지 않는다. 쿠키 사용 시 HttpOnly/Secure/SameSite 및 CSRF 방어가 필요하다.

### 파일과 콘텐츠

- 상대 경로만 API에서 다루고 절대 경로·`..`·드라이브/UNC 탈출·심볼릭 링크를 거절한다.
- 대상은 로컬에서 등록한 일반 파일/관리 구간으로 한정한다.
- 비밀·개인키·회사 자료를 예제나 기본 규칙에 포함하지 않는다. 확장자만으로 비밀이 없다고 보장하지 않는다.
- 규칙은 AI의 행동을 바꾸므로 게시 권한을 민감한 설정 변경 권한으로 취급한다.
- Markdown은 렌더링할 때 안전한 부분만 사용하고, 본문을 명령·템플릿 코드로 실행하지 않는다.
- 요청 크기, 규칙 크기, 기기 수/빈도와 로그 증가량에 한계를 둔다.

### Hub의 책임

Hub는 중앙 신뢰 지점이다. 관리자가 볼 수 있는 규칙 내용과 기기 상태가 저장된다. Alpha는 관리자에게 내용이 보이지 않는 종단 간 암호화 제품이 아니다.

Hub가 멈추면 기기의 기존 규칙 파일은 남지만 새 전파와 중앙 확인은 멈춘다. Hub 데이터·인증 설정·버전 이력은 일관된 방법으로 백업해야 한다. SQLite가 실행 중일 때 DB 파일 하나만 복사해 정상 백업이라고 가정하지 않는다. 복원 후에는 과거 상태로 되돌아간 Hub와 기기의 버전 차이를 재검사하고, 확인 전 최신 상태로 표시하지 않는다.

Alpha는 기기 인증 폐기 후 새 요청을 거절한다. 폐기 전에 이미 받은 규칙과 로컬 파일을 원격으로 회수하거나 지울 수 있다고 약속하지 않는다.

## 13. 오류와 복구 안내

| 상황 | 제품 동작 | 안내 |
| --- | --- | --- |
| Agent 오프라인 | 대기 및 마지막 관측 표시 | 기기 연결 확인 |
| 등록 토큰 만료/사용됨 | 등록 거절 | 새 토큰 발급 |
| 인증 폐기 | 새 요청 거절 | 새 등록 필요 여부 확인 |
| 파일 권한 부족/읽기 전용 | 해당 매핑 중지, 오류 기록 | 기기에서 권한 확인 |
| 루트·대상 디렉터리 소실 | 적용 중지, 대량 삭제 전파 금지 | 경로·마운트 확인 |
| 관리 표식 이상 | 적용 중지, 기존 파일 보존 | 표식 및 등록 내용 확인 |
| 로컬 블록 편집 | 로컬 내용 보존, Hub에 충돌 상태 보고 | 기기에서 차이 확인 후 필요한 내용을 수동 반영 |
| 디스크 부족/임시 파일 실패 | 완료 응답 금지 | 여유 공간 확보 후 재시도 |
| 전송 중 끊김 | 미완료 상태 유지, 게시 버전 재확인 | 재연결 대기 |
| 쓰기 중 프로세스 중단 | 재시작 시 파일·작업 기록 재검사 | 복구 결과 확인 |
| 해시 불일치 | 실패·재확인, 최신 표시 금지 | 로컬 동시 쓰기·저장 오류 확인 |
| Hub 백업 복원 | 버전 재조정 전 확인 오래됨 표시 | 기기별 재검증 |
| 지원하지 않는 파일명/타입 | 명시적 거절 | 지원 범위의 대상 선택 |

사용자가 해결할 수 있는 다음 행동을 오류와 함께 보여준다. API 내부 오류나 비밀이 포함된 원문을 그대로 UI·로그로 내보내지 않는다.

## 14. 단계별 구현과 수용 기준

### 단계 A — 기반과 계약

- 규칙 팩, 게시 버전, 기기, 매핑, 정책, 관측의 데이터 모델과 API 확정.
- 인증 분리, 요청 크기 제한, loopback/HTTPS 경계 구현.
- 수용: 미인증 요청 거절, 권한 혼용 거절, 잘못된 경로/크기 거절, 오래된 초안 기준 버전 거절.

### 단계 B — 규칙 편집과 게시

- 웹 편집·미리보기·초안·게시·이력·이전 내용의 초안 복원 구현. 상세 비교 화면은 후속 개선 가능.
- 수용: 두 브라우저가 같은 기준에서 게시할 때 하나는 충돌, 초안은 Agent가 받지 않음, 이전 버전 내용으로 새 버전 생성, Markdown 스크립트 미실행.

### 단계 C — 기기와 관리 블록 적용

- 일회용 등록, 로컬 경로 등록, 게시본 확인, 관리 블록 적용, 백업, 해시 확인.
- 수용: 두 기기에 같은 게시 버전 설치, 관리 블록 밖 바이트 보존, 중복/손상 표식 거절, 로컬 내부 편집 보존, 경로 탈출/심볼릭 링크 거절.
- Codex/Claude Code 프로필은 각 앱이 파일을 발견하는지 별도 검증한다. 확인하지 못한 환경은 미확인으로 표시한다.

### 단계 D — 관측과 실패 복구

- 주기/수동/중지 정책, 지금 동기화 세대, 기기별 관측, 오래된 상태, 충돌 상태 안내.
- 수용: 한 기기 오프라인 중 게시→대기→재접속 설치 확인; 이전 ack가 최신 버전을 성공 처리하지 않음; 재시작 후 미완료 작업 유지; 루트 소실이 삭제를 유발하지 않음.
- 전송/쓰기/ack 경계에서 프로세스를 중단해도 재시도로 일관된 상태에 수렴하며 보존본을 확인할 수 있어야 한다.
- 외부 편집기와 경합하는 시나리오를 검사하고 관측된 한계를 릴리스에 적는다.

### 단계 E — 공개 Alpha

- README, 설치·보안·백업·복원·제거·기여 안내, 라이선스, 알려진 한계.
- 공개 데이터 검토: 실제 회사 자료·개인 규칙·인증정보·기기별 사적 경로가 없음.
- 단위/통합 테스트와 실제 두 Agent 실증 결과를 분리해 기록.
- macOS·Linux의 빌드/실행/파일 적용 검증 범위를 각각 표시.
- 공개된 버전을 운영 데이터 없이 새 폴더에서 시작해 예제 규칙의 편집→게시→설치 확인→충돌 보존→복구를 재현.
- 미완료 기능은 비활성화하거나 명확히 계획으로 표시. 계획서의 모든 기능을 이미 구현했다고 소개하지 않는다.

## 15. 공개 저장소와 배포 원칙

- 독자 구현을 기본으로 하고 외부 프로젝트 코드를 복사하지 않는다. 의존성 라이선스와 배포 고지는 별도 확인한다.
- 제품 저장소에는 실행 중 생성되는 DB, Agent 설정/인증, 백업, 실제 규칙 자료를 커밋하지 않는다.
- 예제는 가상의 기기와 규칙을 사용한다. 설치 명령에 실사용 토큰을 포함하지 않는다.
- 저장소 공개와 실행 서비스 인터넷 공개는 다르다. 코드 공개를 이유로 Hub를 자동 외부 노출하지 않는다.
- 초기 공개는 Alpha로 표시하고 검증 범위·알려진 한계·보안 신고 방법을 함께 제공한다.
- 릴리스는 빌드 출처·체크섬·지원 플랫폼을 제시한다. 서명/공급망 강화는 후속 단계로 분리하고 현재 수준을 정확히 적는다.

## 16. 후속 확장

- Windows Agent 지원과 운영체제별 파일 시스템 검증.
- 로컬 수정본의 선택적 업로드와 원격 차이/병합 화면.
- 한 파일의 멀티팩 합성과 명시적인 우선순위.
- 삭제 전파·tombstone·범용 작업 ID는 필요성이 확인되면 별도 프로토콜로 설계.
- 작은 일반 파일(예: 최대 10 MiB) 동기화는 규칙 배포와 구분된 후속 제품 범위.

- 프로젝트별 규칙 팩과 회사/개인 환경의 명시적 분리.
- Git에서 가져온 승인 변경과 게시 버전의 연결.
- 앱별 규칙 발견 진단 및 근거 수집 도구. 파일 해시와 모델 행동은 계속 분리한다.
- 선택적인 읽기 전용 기기·관리자/검토자 분리.
- 규칙 팩 간 관계·우선순위 시각화 및 검토 가능한 병합 제안.
- 관리형 업데이트, 서명된 릴리스, 더 강한 운영 감사와 백업 도구.

이 확장들은 첫 버전의 안정적인 게시·보존·관측 흐름을 검증한 뒤 진행한다.
